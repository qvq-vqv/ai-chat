# 主动调用端能力

主动调用端就是用户交“一键启动”的 AI。目标适配器负责“把消息投递到哪、如何读回”；调用端通常不需要自己被接收的适配器。若采用双向主动投递，两个方向分别需要目标适配器，且不能出现两个调度者互相催发。

## Antigravity 主动员工

已在本机安装 ai-company 与 ai-chat。启动时核实当前会话实际能读取这些文件、调用 Node/目标 CLI、执行项目合同并持续等待。典型是本地命令+项目文件工具；仅软件安装或技能软链接存在，不证明当前对话已加载工具。

向 Antigravity 对话投递还需软件提供的原生认证环境；不能假设在任意外部终端都能调用 agentapi。

调用 Codex 时使用 codex-session，不使用 antigravity-session；后者只在其他 AI 需要向 Antigravity 对话投递时选择。调用 WorkBuddy 时需选择其实际入口，并满足网络/官方 OAuth 要求。不要自动切换当前模型或放宽终端权限。

## WorkBuddy 主动员工

已在本机安装同一份 ai-company 与 ai-chat。核实当前会话能执行本地命令、访问项目文件和等待；不要求 WorkBuddy OpenAPI 令牌才能主动调用本机 Codex/Antigravity 适配器。**OpenAPI 令牌仅在把 WorkBuddy 本地助理当作被调用目标时才需要。**

WorkBuddy 的内置 CLI 与当前桌面会话不是默认同一个运行入口，不能为了“预检查调用端”擅自启动另一 CLI 会话。能力检查由当前员工在自己的工具环境完成。

## 现场检查和持续性

当前员工亲自确认能读项目和技能、运行 node --version、使用目标适配器执行只读 preflight。确认后握手中自行完成发送—等待—读回—下一动作，才能验证当前调用端可用。涉及目标项目写回复文件时须确认共享项目和写入权限。

第一次等待 45 秒后若仍未完成，应在原任务内续等同一 request_file，而不是要求用户说继续。工具/平台结束对话时准确记录中断；本文件不会自动唤醒 AI。能力可记录在绑定 employee.capabilities，来源是实测，不是硬编码软件品牌。
