# 从零启动项目

用户要新开项目、仅有想法、为空目录建立公司时读取。具体团队定制按本模块规划；讨论或评审不等于批准创建真实项目、启员工或发送消息。当前运行基线仍是一个固定架构师和一个员工。

## 先判断入口

| 现场事实 | 分支 | 下一动作 |
|---|---|---|
| 只有想法，未选目录 | 规划 | 整理目标草案，建议目录；合并询问缺失的关键选择，未选根目录不落真实项目文件 |
| 已选新目录，目录不存在或为空 | 新建 | 检查父目录、实际路径和允许创建范围，预览最小文件清单 |
| 已有代码、README、规则或计划 | 接入 | 先读权威入口；补缺项，不强制改结构，不把已有资料当空项目 |
| 已有绑定或未决请求 | 恢复 | 先按runtime恢复原binding/state-dir/handle；不重复握手、换project_id或state-dir绕过归属 |

核实显示路径和实际路径。软链接可以是合法入口，但实际目标须在用户批准范围；不猜测归属或向其他项目写入。目录出现新文件、当前版本改变或权限不足时暂停受影响写入，报告具体差异，独立规划继续。

## 把想法变成可执行第一阶段

按[项目蓝图](project-blueprint.md)的预填责任和四项要求，由当前AI先给可审阅草案、总架构师负责定稿，不把空表转交用户。预填：用户原目标、使用对象、可观察成果、非目标、关键约束、未知项、阶段与验收。记录来源为用户事实/已有资料/建议/未知，不把建议技术栈、预算或岗位写成已确认。

未知项会改变目标、成本或主要方案时，先安排最小探索合同：只读调研/样例分析，产出方案与取舍，明确停止条件；别直接下“做完整产品”。目标已足够明确时直接拟首个可验收增量，避免强加探索阶段。已有等效授权覆盖的路径/写入范围直接沿用，不重复要求确认。

业务定制按“目标 → 工作流程 → 必要职责 → 产物/审查”规划。先给最小配置和分设岗位的实际收益，不按人名、星座或行业标签推定能力。一个员工可在有界合同中先后承担研究、制作、文档职责，但不能把同一执行主体自审称为独立审核。需要并行、不同权限或独立专业审查时再提出独立岗位；未配置岗位保持候选，按work-records登记。没有多岗位调度实现时明确缺口，不给schema2塞多员工字段。

## 最小初始化清单

先展示目标目录、创建/复用/修改项、原因及具体授权依据。文件确认和角色/通信配置可合并成startup的一份配置，不能把授权切成无意义的多轮。材料已齐全且用户明确批准建立此项目时执行覆盖内动作。

| 项目需要 | 建议位置 | 原则 |
|---|---|---|
| 目标、阶段、非目标和验收 | 既有README/OpenSpec；没有则PROJECT.md | 一个权威蓝图；其他入口只指向它，不平行复制 |
| 跨轮状态与初始化回执 | 既有项目状态；没有则.ai-company/project-state.md | 仅多步骤工作需要；记录本轮事实、恢复位置和文件清单 |
| 绑定与请求 | .ai-company/binding.json及该适配器state-dir | 只按startup/runtime建立；未握手不标ACTIVE |
| 讨论原文与变更理由 | 已有项目档案 | 遵守当前档案规则；必要时建立项目档案，不把私人讨论放公开包 |

不因开项目自动git init、npm install、OpenSpec init、复制全局AGENTS、建后台服务或批量建会话；具体任务确实需要且获准时采用。不存在目录的创建须在已批准父目录内；不创建真实业务代码骨架来冒充启动验收。

写文件前检查存在性与当前版本：新文件使用排他创建，已有文件先读再做最小补充；发现既有未知内容停止覆盖。保护私有运行资料不进入发布包：已有Git项目先核对忽略规则并在授权内补必要项；没有Git时记录将来公开前排除清单。不要改无关忽略规则或把全文私人记录交给远端。

## 初始化中断或部分失败

每个完成动作及时登记路径、创建/修改、原文件基线（如有）、完成后哈希、来源及下一动作。失败时记录已成功项、失败点和未知状态，不删整个新目录作为回滚。

续接先读回执并比较当前文件：缺项可在原授权内续建；存在且内容相符就复用；内容不同先保留并判断冲突。移除/还原只涉及本轮拥有、当前内容未被他人改动且恢复已核实的文件；原授权未覆盖材料删除时不自行删。共享文件、旧请求、锁和会话不随初始化失败清除。

文件准备完成后进入[startup](startup.md)的角色/会话确认与握手；不重新填一份配置。当前AI是架构师时按原职责准备合同与员工接入说明，不能伪装员工发起请求。通信失败保留文件产物和原handle，按runtime标BLOCKED/SUSPENDED；文件准备和通信可用分别报告。

## 验证记录与首阶段交付

每项填证据、责任人及VERIFIED/NOT_VERIFIED/NOT_APPLICABLE（后者注明理由），不是向binding添加新状态：

1. 根目录和项目身份正确，权威蓝图可读；新建/复用清单核对，已有文件保留。
2. 第一阶段及首合同的产物、验收、资源写入者与授权可追溯。
3. 所需技能依赖可定位，员工工具能力和准确目标的通信握手真实读回；缺口用DRAFT/BLOCKED记录。
4. 员工执行首合同、提交，架构师独立复核并发裁决，员工读回匹配裁决。
5. 员工主动REQUEST_TASK，连续第二份合同正确关联；没有合同不自定业务施工。
6. 实际中断后保留文件基线/绑定/原handle，恢复不重投；收尾核对未决影响与入口责任。

离线文档自审、隔离文件操作、模拟JSON检查、真实双会话和长期运行分别标来源。可复用未变且适用的用户已确认通信长期证据，不机械重测；它不代替新项目归属、主动协作或业务验收。尚缺现场证据就交付准备结果与准确缺口，不声称从零全链路或无人值守已验收。完整Goal仍按acceptance/closure裁定。
