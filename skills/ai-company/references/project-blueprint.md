# 项目蓝图与按需团队规划

与[new-project](new-project.md)一起读取。下面是可填写的工作模板，不是新协议，不自动创建项目、岗位或运行状态。简单任务只填写影响执行的项；已有OpenSpec/README中的权威内容直接引用，未知事实保留未知。

## 谁负责预填

当前接到项目请求的AI先用用户目标和已有资料预填完整可审阅草案，不把空表交给用户逐项填。已确定总架构师时，由总架构师负责蓝图定稿、职责分配及首合同；员工提供输入清单、工具/技能能力证据和实施约束，并可提出草案供架构师核对。架构师尚未接通时保留草案及待裁决项，不自任第二角色。

能合理提出的内容先写建议，并解释原因；不可推断的事实写“未知＋需要谁核实”，不编造项目经验、工具权限、会话身份或标准合规。只向用户合并询问会改变目标、成本、主要方案或授权的关键选择，不要求用户替AI设计岗位表。自动预填是当前AI执行指导，不是后台岗位调度或自动创建员工。

## 四项预填要求

1. **业务岗位：** 从可观察成果倒推必要工作，列执行/审查职责、产物、所需工具或专业能力及核实依据；先推荐最小配置，并说明何时才需要独立岗位。能力声明与实测证据分别写。
2. **流程链：** 给可读的“输入 → 加工 → 审查 → 交付”链；每个交接有产物/版本、接收职责与通过条件，必要时加分支、返工或升级位置。不能只画箭头而没有实际交接内容。
3. **共享支撑：** 主动评估文档标准化、资料管理、数据/工具处理等共用工作；写服务对象、负责职责和交付。工作量小就合并到已有员工，有独立需求再建议分设；不适用时写理由，不硬建支撑会话。
4. **输出表达：** 根据用户和使用对象预填语言、格式、术语解释、细节程度、语气与必要长度限制；把影响验收的要求带入合同并给核验方法。用户已明确偏好直接沿用，其他标建议；人名/星座只作可选风格，不计专业能力或质量通过。

交付草案前核对四项均有内容、引用或不适用理由，尤其检查人数/岗位清单、管理与交接关系一致。若只有一个员工承担多个职责，明确是职责复用，不冒称独立多人。

## 非业务示例：两份只读规则审查合同

目的：在授权的隔离演练项目检查流程，不替用户开发业务产品。阅读两份指定的非私密规则文件，产出各自的缺漏表；“正确接收第一份验收并主动申请第二份合同”是协作测试目标，不能只以报告存在算通过。

- 第一阶段：架构师给A1合同，只读文件A，员工交R1；独立审查核对每项结论确有输入依据，给匹配裁决，员工读回。
- 第二阶段：员工主动申请A2；架构师给只读文件B的合同，员工交R2，独立验收再核对关联及安全收尾。A2在正式ASSIGN前只是计划，不是新授权。
- 最小运行岗位：固定架构师＋一个员工。员工可完成资料整理与报告排版；不要为了两个小报告再建文档/数据会话。专业证据需要额外独立审核时，说明具体收益与能力缺口再提议岗位。
- 离线准备可只填写样例合同和静态检查，状态NOT_VERIFIED。只有真实收发与独立复核证据才能计入现场验证。

示例可按实际目标缩放；不限制真实项目必须做两份规则报告。不照搬第三方行业团队人数或专业能力声明。实际定制在用户提供项目目标和限制后完成。
